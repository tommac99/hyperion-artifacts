The Architectural Bet
Medusa v2 is the spine; everything else is a satellite.

The single most important architectural commitment is that Medusa is the source of truth. Every booking — whether it originates on our website, on Viator, on GetYourGuide, on Jochen Schweizer, or as a manual entry by Jannis — exists as a row in Medusa's database. External systems are satellites we sync to, never sources of truth. This rule is what stops the current Zapier mesh's failure mode from re-emerging.

02 · Foundation Choice

Why Medusa, Specifically

Three patterns from Medusa v2 do the structural heavy lifting for us — modules, workflows, and sales channels. Each maps directly onto a problem we'd otherwise solve from scratch.

Modules → Domain isolation, swappable services
Pattern · Boundary discipline

A Medusa module owns its own data, its own service class, and its own migrations. Modules expose a service interface; they never reach into each other's tables. This is the discipline that keeps the codebase readable as it grows from one boat to twenty.

We ship with the built-in modules (product, cart, order, customer, pricing, promotion, tax, stock-location, sales-channel, gift-card, stripe) and add six custom modules: bookings, boats, shifts, safety, accounting, migration.

Why this matters: if Bókun ever changes their API or we want to swap notification providers, only the relevant module changes. The rest of the codebase doesn't notice. 

// src/modules/bookings/index.ts — example custom module shape
import { Module } from "@medusajs/framework/utils"
import BookingsService from "./service"

export const BOOKINGS_MODULE = "bookings"

export default Module(BOOKINGS_MODULE, {
  service: BookingsService,
})
Workflows → Saga pattern with free compensation
Pattern · Transactional integrity

A workflow is a typed sequence of steps. Each step can declare a compensation — what to do if a later step fails. The framework guarantees that if step 4 fails, steps 1-3 get their compensations called in reverse order. This is the saga pattern, free.

Critical for us because a booking creation touches multiple modules: bookings (reserve slot), cart (price line items), customer (create or attach customer), payment (Stripe intent), order (finalize). Any of these can fail. Without saga discipline, a partial failure leaves the slot reserved but no payment captured — a phantom booking. 

// src/workflows/create-booking.ts
import {
  createWorkflow,
  WorkflowResponse,
} from "@medusajs/framework/workflows-sdk"

export const createBookingWorkflow = createWorkflow(
  "create-booking",
  (input: CreateBookingInput) => {
    const lock = acquireSlotLockStep(input)            // Redis lock
    const verified = verifyAvailabilityStep(input)     // SELECT FOR UPDATE
    const booking = reserveBookingStep(verified)         // status=pending
    const cart = createBookingCartStep(booking)          // medusa cart
    const intent = createPaymentIntentStep(cart)        // stripe
    return new WorkflowResponse({ booking, cart, intent })
    // If reserveBookingStep succeeds and createPaymentIntentStep fails,
    // the booking row is auto-rolled back via the compensation handler.
  }
)
Sales Channels → Native franchise multi-tenancy
Pattern · Data isolation by design

Medusa's Sales Channel module exists so a single product catalogue can be sold through different storefronts with different pricing and availability. We repurpose it as the franchise primitive: each Badedampfer location (Berlin, Vienna, Wörthersee in 2028) is a Sales Channel.

Every Boat, every Booking, every Stripe Connect account, every staff member is scoped to a Sales Channel ID. Queries that don't pass a channel filter return zero rows by default (enforced in the service layer). Berlin admins see Berlin; Vienna admins see Vienna; central admin (Jannis) sees everything.

This is what makes adding Wörthersee a configuration change in Year 3 rather than a refactor.

03 · The Stack

Each Piece, in Detail

What each component does, why it's here, what version, and the one thing that could trip us up about it. Open the rows that interest you.

Medusa v2
Commerce backbone · Node.js / TypeScript · MIT

What it does: the four-layer commerce engine — API routes, workflows, modules, Postgres data store. Provides cart, order, customer, product, pricing, promotion, gift-card, tax, sales-channel, stock-location, and Stripe modules out of the box.

Version target: latest stable v2. Pin to a specific minor (e.g. 2.4.x) at install; upgrade deliberately, never on autopilot.

Watch out for: v2 is a substantial rewrite from v1; the community docs are still catching up in places. When the official docs are thin, read the source — Medusa is open-source for a reason. Don't take random tutorial code from 2023 — most of it is v1 and won't work.

PostgreSQL 16
Primary database · Self-hosted, replicated

What it does: source of truth for everything. Medusa uses MikroORM as its data mapper and runs migrations through it.

Why Postgres specifically: we need SELECT ... FOR UPDATE row locks for the booking race-condition problem. We need JSONB for the metadata fields. We need tstzrange for time-range columns if we go down that road for advanced availability queries. Postgres gives us all three.

Watch out for: connection pooling. Medusa workflows can hold connections during long steps; we'll need PgBouncer in front in production. Set statement_timeout on the connection pool to prevent runaway queries.

Redis 7
Cache · Queue · Distributed locks

What it does: three jobs. (1) Job queue via BullMQ (cron schedules, async work, retries). (2) Cache for hot reads like "is this slot available?" — the same query a customer hits when browsing. (3) Distributed locks for the booking concurrency problem.

Watch out for: persistence. We must run Redis with AOF persistence enabled (appendonly yes), not the default RDB-only mode — otherwise a Redis crash loses in-flight jobs. For locks specifically, use Redlock pattern with explicit TTLs so a crashed worker can't permanently hold a slot reservation.

Next.js 16 (Turbopack)
Customer site · Admin extensions · TypeScript

What it does: two surfaces. The customer-facing booking site at badedampfer.de (and .at). Custom admin pages that extend Medusa's built-in admin where its UI isn't enough — daily ops view, safety checklist UI, accounting export panel.

Turbopack: dev-server speed matters for builder velocity. Pin Turbopack at production-stable; webpack is the fallback if any caching bug bites.

Watch out for: server components vs client components is a real architectural decision per page. Booking calendar interaction is client-heavy; the home page can be RSC. Don't blanket either way.

Stripe (Payments · Connect · Tax)
Money layer · Test mode in dev · Live keys via secrets vault

Stripe Payments: the obvious — card processing. PaymentIntents API, server-side confirmation, 3DS where required (mandatory in EU).

Stripe Connect: franchise splits. Each franchise location (Berlin, Vienna...) is a Connected Account. Payments come into the platform account; the share for that location is transferred immediately via application_fee_amount. Berlin's money lands in Berlin's Stripe; Vienna's in Vienna's; platform fee stays with the central entity.

Stripe Tax: automatic VAT calculation per jurisdiction. Customer in DE sees DE VAT; customer in AT sees AT VAT; B2B customers with valid VAT IDs get reverse-charge. The Tax product is rented for this reason — being wrong on VAT is a tax problem, not a feature bug.

Watch out for: the difference between destination charges (Connect account receives payment directly) and separate charges + transfers (platform receives, then transfers). For our model — central brand, distributed locations — separate charges + transfers is correct. Get this wrong day one, refactoring later is painful.

Bókun API
OTA bridge · Free for suppliers · TripAdvisor-owned

What we use: the Supplier API. Two operations are foundational: POST /availability to push our slot availability to Bókun (so OTAs see it), and webhooks booking.created / booking.cancelled to receive OTA bookings into our system.

Watch out for: Bókun's API has improved a lot but isn't Stripe-quality. Expect: occasional 5xx responses, inconsistent date formatting in some endpoints, eventual-consistency on availability writes. We build defensively — retry with exponential backoff, idempotency keys on every write, a periodic reconciliation job that compares our state to Bókun's and flags drift.

Novu (Self-Hosted)
Notification orchestration · MIT · Docker

What it does: one API call from us; Novu fans out to the right channels (WhatsApp, email, SMS) based on user preferences. Templates managed in Novu's UI so we don't redeploy to change the wording of a confirmation email.

WhatsApp specifically: Novu connects to WhatsApp via Twilio or Meta Business API. Twilio is faster to set up but more expensive per message; Meta Business is cheaper at scale but takes weeks to approve. Start Twilio, migrate later.

Watch out for: Novu's self-hosted version requires its own Postgres/MongoDB/Redis. Adds infra surface. Worth it for control; not worth it if we're going to be fighting their deployment more than building features.

Documenso (Self-Hosted, AGPL)
Digital waivers · Via API only · Never modify source

What it does: sends the safety waiver to the customer pre-trip; collects a legally-valid digital signature; stores the signed PDF; fires a webhook back to us when signed.

Why API-only matters: Documenso is AGPL-licensed. If we modify the source, we are obligated to publish our modifications. Using it as an external service via REST API does not trigger this — the AGPL boundary is "you must distribute source if you distribute the modified binary." We don't distribute, and we don't modify, so we are safe.

Our integration: our bookings module hits Documenso's POST /documents endpoint to send a waiver pre-fill, sets a webhook to our POST /webhooks/documenso endpoint, updates the booking row's waiver_signed_at when the webhook fires.

Twenty (Self-Hosted, AGPL)
CRM for franchise partners + B2B · Via API only

What it does: CRM for non-end-customer relationships. Franchise partner pipeline (potential Wörthersee operators), B2B accounts (hotel concierges, corporate event buyers, embassies in Vienna), press contacts.

Why separate from Medusa customers: end customers are a different domain — high volume, transactional, retention-focused, hosted in Medusa's customer module. CRM relationships are low-volume, narrative, pipeline-focused. Forcing both into one table is the classic CRM-bloat mistake.

Same AGPL rule as Documenso: we never modify the source.

Sentry
Error tracking · Performance · Release health

What it does: catches every unhandled exception in both the Medusa backend and the Next.js frontend, groups them by stack-trace fingerprint, alerts on new errors, gives us session replays for frontend bugs.

The free tier is enough for the first six months. Paid plan starts mattering when we cross ~50k events/month.

Watch out for: sample rate. Default 100% sampling will burn through quota fast. Set tracesSampleRate to 0.1 in production for performance traces, 1.0 for errors (always).

Cloudflare R2 (S3-compatible)
Object storage · Zero egress fees

What it stores: customer photos (post-trip), signed waiver PDFs, DATEV export files (kept for audit), invoice PDFs.

Why R2 over S3: Cloudflare R2 charges nothing for egress. AWS S3 charges per GB out. For a business that serves photos and PDFs on every page view, this is a meaningful cost difference at scale.

Watch out for: R2 doesn't have full feature-parity with S3 — but everything we need (PUT, GET, signed URLs, lifecycle rules) works. Don't use any S3-specific features like Object Lock without checking R2's support page.

PostHog
Product analytics · Self-hostable · Free tier generous

What it does: tracks the customer booking funnel — landing page view, slot picker opened, add-on selected, checkout started, payment confirmed. Tells us where customers drop off.

Why not just Google Analytics: GA4 is great for traffic acquisition; PostHog is better for product funnels. We want both — GA for marketing dashboards, PostHog for product decisions.

DATEV / Lexware Integration
Custom module · CSV-based export · No API

The reality: DATEV doesn't offer an open API for the standard chart-of-accounts integration most German accountants use. The accepted exchange format is a CSV export following the DATEV-Format specification.

What we build: a custom accounting module with one main job — generate a monthly DATEV-compliant CSV. The format is well-documented; libraries exist but most are abandoned, so we'll write our own thin generator. Same module also supports Lexware as a swappable output format.

Watch out for: the German chart of accounts varies by accountant (SKR03 vs SKR04). Talk to the Badedampfer Steuerberater early to confirm which one and to lock the account mappings. Hardcoding the wrong one means re-mapping every transaction later.

04 · The Booking Engine

The Hard Part,
Where Cal.diy Helps

The booking engine is the one piece where most amateur platforms quietly break. Three problems make it hard: timezones and DST transitions, availability under concurrency, and recurring patterns with exceptions. Cal.diy's MIT-licensed scheduling code is our reference for the first and third; we solve concurrency ourselves in Postgres.

What "availability" actually means

A boat is available at a moment in time when: (1) a time_slot_template says that day-of-week and time-of-day are operating hours, (2) no availability_exception overrides that day to closed, (3) no existing booking with status in (pending, confirmed, checked_in) overlaps that time range. The third condition is where concurrency bites.

Three queries, in order

The availability check is a sequence: cheap reads first (use the cache), expensive checks last (hit the database with locks only when committing). The customer-facing "show me what's available next Saturday" view runs against a denormalised availability cache in Redis, refreshed by a cron. The actual booking write runs the expensive SELECT FOR UPDATE path.

What we borrow from Cal.diy
Logic only · We don't fork the app

Cal.diy's getAvailability module is the gold standard for: combining recurring schedules with date-specific overrides, handling DST transitions correctly across timezones, calculating buffer times between bookings without off-by-one bugs, supporting "team" schedules where multiple resources are bookable.

How we use it: our bookings module's computeAvailabilityForBoat(boat_id, date_range) function studies Cal.diy's implementation, takes the logic patterns (especially the timezone handling and the buffer math), and rewrites them into Medusa-idiomatic code. We do not import the Cal.diy package; we write our own function using their MIT-licensed source as a reference.

Why not just import it: Cal.diy is a full app with auth, multi-tenancy, plugins. Importing the package would pull in 200+ transitive dependencies. We want the math, not the app.

Timezone handling rule
Everything UTC in DB · Render local in UI

Every timestamp in the database is stored as timestamp with time zone, normalised to UTC. When the customer-facing site renders a slot, it converts to the customer's browser timezone (or Berlin/Vienna if no browser hint exists). When the OTA pushes a booking from a different timezone, we normalise on ingest.

The classic mistake: storing local-time without TZ and reasoning about it as if it were UTC. Day-saving transitions in March and October will eventually produce a phantom 3am booking or skip a 2:30am slot that should have existed. Postgres timestamptz + the luxon library on the application side prevents this.

Buffer time
Turnaround between rentals · 30-45min default

Between two consecutive bookings on the same boat, we need turnaround time: clean the tub, refill if needed, briefing the next group. This is a per-time_slot_template field buffer_minutes with a sensible default of 30 minutes.

Availability computation must respect buffer. A 14:00-16:00 booking with a 30-minute buffer makes the 16:00-18:00 slot unavailable on the same boat — but available on the next boat. Easy to get wrong in the SQL.

06 · Workflows

The Saga Pattern,
Used Properly

Workflows are how Medusa v2 expresses transactional intent that crosses multiple modules. Each workflow is a sequence of steps; each step has a compensation. If step N fails, steps 1...N-1 get their compensations run in reverse. This document lists the workflows we own and what they touch.

create-booking
Steps: 6 · Critical path

The customer's "Book Now" hits this. Touches bookings (lock + reserve), cart (create + add line items), customer (create or attach), stripe (PaymentIntent), order (create on payment), novu (confirmation notification).

Compensations on failure: release slot lock, mark booking cancelled, void PaymentIntent, delete cart. No phantom rows left.

cancel-booking
Steps: 4 · Customer-initiated or staff-initiated

Updates booking status, frees the slot, calculates refund amount per the cancellation policy, issues Stripe refund, sends cancellation notification, syncs cancellation to Bókun if OTA-originated.

import-ota-booking
Steps: 5 · Triggered by Bókun webhook

OTAs collect payment themselves, so this workflow doesn't touch Stripe. It does: verify booking doesn't already exist (idempotency on Bókun id), create customer if new, reserve slot via the same lock pattern as direct bookings (with conflict resolution if the slot has somehow been double-sold), create booking with source_channel set, fire welcome notification, log to safety reminder queue.

Edge case: Bókun marks a slot booked while we marked it booked from a direct customer in the same minute. Our exclusion constraint will reject one. The losing side gets retried with the next available slot suggestion to staff for manual handling. This will happen occasionally; it must not crash the system.

redeem-voucher
Steps: 4 · JSMD vouchers + own gift cards

Validates voucher code with the voucher provider (Jochen Schweizer / mydays API or our own gift_card module), applies the credit to the cart, completes the booking. Handles partial vouchers (€200 voucher used for €150 booking → remaining €50 is either lost, refunded to provider, or kept as credit, depending on JSMD's rules; our default is "lost" because that's their standard).

generate-accounting-export
Steps: 3 · Run monthly via cron

Queries all orders + refunds + voucher redemptions for the period, applies the chart-of-accounts mapping, generates the DATEV CSV, uploads to R2, records the export in accounting_exports, emails the accountant a download link.

07 · Scheduled Jobs

Cron — Everything
That Runs on a Schedule

Medusa v2 jobs run via the in-process scheduler backed by BullMQ on Redis. Schedules in standard 5-field cron format. Every job is idempotent — running it twice produces the same result as running it once.

expire-pending-bookings */10 * * * * Find bookings in status=pending older than 15 minutes (cart abandoned). Run the cancel-booking workflow on each — releases the slot.
refresh-availability-cache */3 * * * * Recompute the public availability view for the next 14 days and write to Redis. The booking-flow's first query hits this cache.
send-trip-reminders 0 * * * * For each booking starting in [23h, 25h] from now, send the 24-hour reminder via Novu (WhatsApp + email).

08 · Event Subscribers

What Fires
When Things Happen

Medusa v2 fires events on state changes. Subscribers are event handlers that react asynchronously. We use them for the "side effects" — notifications, syncs, logs — that aren't part of the core transactional flow.

EventSubscriberWhat It Does
order.placed on-order-placed Confirms the related booking (status → confirmed), fires confirmation notification, schedules waiver request, syncs to Bókun if direct booking, increments Sales Channel revenue counter.
booking.confirmed on-booking-confirmed Queues Documenso waiver send, refreshes availability cache for that boat, logs to PostHog event stream.
booking.cancelled on-booking-cancelled Frees the slot (cache invalidate), syncs cancellation to Bókun, schedules refund via Stripe if applicable, notifies customer + ops.
documenso.signed (webhook) on-waiver-signed Sets waiver_signed_at on the booking. Stores signed PDF path in R2. Notifies ops "ready for check-in".

10 · The Race-Condition Problem

Two Customers,
One Last Slot

The classic booking-system bug. Two customers click "Book" at 14:00:00.000 for the last 15:00 slot Saturday. Without explicit protection, both can succeed. The platform sells the same boat to two parties. Operationally catastrophic; we engineer to make it impossible.

Three lines of defence

Belt, braces, and a safety net. Each one alone is sufficient most of the time; together they make the race impossible.

Defence 1 — Redis distributed lock (cheap, fast, application-level)

At workflow step 1, acquire a Redis lock keyed by booking-slot:{boat_id}:{starts_at} using the Redlock pattern. TTL: 30 seconds (longer than the slowest payment-intent creation). Two concurrent requests for the same slot: one acquires, the other gets SLOT_CONTENDED and is told to retry.

Defence 2 — Postgres SELECT FOR UPDATE (transactional)

Inside the create-booking transaction, after the Redis lock is held, we do SELECT id FROM bookings WHERE boat_id = $1 AND tstzrange(starts_at, ends_at) && tstzrange($2, $3) AND status IN ('pending','confirmed','checked_in') FOR UPDATE. This row-level locks any existing overlapping bookings; we then check the result count is zero before inserting.

Defence 3 — PostgreSQL exclusion constraint (database-level guarantee)

The hard wall. We add a GIST exclusion constraint that physically forbids two overlapping bookings on the same boat for active statuses. If somehow (bug, attacker, time-travel) two writes try to land in the same instant past defences 1 and 2, Postgres rejects the second insert at the database level. Application code catches EXCLUSION_VIOLATION errors specifically and returns SLOT_NO_LONGER_AVAILABLE to the client. 

-- The constraint that makes double-booking impossible at the DB level
ALTER TABLE bookings
  ADD CONSTRAINT no_overlapping_bookings
  EXCLUDE USING GIST (
    boat_id WITH =,
    tstzrange(starts_at, ends_at) WITH &&
  )
  WHERE (status IN ('pending', 'confirmed', 'checked_in'));
Tested under load
2000 concurrent requests for the same slot → exactly 1 succeeds

Before going to production, we write a load test that fires 2000 simultaneous booking requests for the same boat/slot from different sessions. The expected (and required) outcome: exactly one returns success, 1999 return SLOT_NO_LONGER_AVAILABLE. If any other outcome — two successes, zero successes, a 500 error — production gets blocked until the issue is fixed. This test runs in CI on every PR that touches the bookings module.

11 · External Integrations

The Outside World

Every external integration sits behind an adapter — a single file in src/modules/<name>/adapter.ts that exposes a clean interface to the rest of the codebase. Switching providers (e.g. swapping Novu for Twilio direct) means changing one file.

Bókun adapter
Module: channels-bokun · The OTA bridge

Exposes: pushAvailability(boat_id, slots[]), handleIncomingBooking(bokun_payload), cancelBookingInBokun(bokun_id, reason). Behind it: HTTP client with retry middleware, signature verification, idempotency-key generation.

Defensive choices: every outbound request carries an idempotency key (Bókun's API supports this). Failures hit a dead-letter queue we monitor. Reconciliation cron catches webhook misses.

Stripe adapter
Already provided by Medusa's Stripe Module · We extend

Medusa ships with a Stripe payment provider module that handles basic charges. We extend it for the Connect-specific flows — application_fee_amount, destination transfers, dispute handling.

JSMD voucher adapter
Jochen Schweizer + mydays · Same portal

Exposes: validateVoucher(code), redeemVoucher(code, amount). JSMD's portal is comparatively basic; expect to find inconsistencies between documentation and actual API behaviour. Build with explicit logging from day one so the inevitable support tickets we file at JSMD can be backed up with request/response dumps.

Documenso adapter
Waiver signing · Self-hosted, REST API

Exposes: requestWaiverSignature(booking, customer), fetchSignedDocument(doc_id). Templated waivers stored in Documenso's UI; we reference by template ID and pre-fill customer details.

Twenty CRM adapter
Franchise partner + B2B pipeline

Exposes: upsertCompany(), upsertContact(), logActivity(). Used when a booking comes from a corporate channel or when a franchise enquiry hits the contact form.

Novu adapter
One API, multiple channels

Exposes: trigger(templateId, subscriberId, payload). Subscribers in Novu map to Medusa customer IDs + staff IDs. Templates are managed in Novu's UI — copy changes are not deploys.

DATEV adapter
CSV generation, no live API

Exposes: generateDATEVCSV(transactions[], skr_version). Implements the DATEV-Format v8 specification. SKR03 vs SKR04 selection is a config flag set per legal entity.

12 · Multi-Tenancy

Franchise Isolation,
in Practice

Every booking, customer (where collected by location), boat, shift, safety log, and accounting export is scoped to a sales_channel_id. The rule is enforced in the service layer — base classes require a channel scope on every query.

The scoping discipline
Enforced in code · Tested explicitly

We extend Medusa's repository pattern with a ScopedRepository base class. Every list(), find(), findOne() requires a sales_channel_id in the filter. Calls without it throw at compile time (TypeScript discriminated union) and at runtime (defensive guard).

A dedicated test suite — multi-tenancy.test.ts — runs on every PR. It seeds two channels, creates data in each, then attempts cross-channel reads. Any leak fails the build.

Admin authentication scopes
Who sees what

Staff accounts have a scope: either a specific sales_channel_id or "global" (only the founding team). The JWT carries this; every request validates that the queried scope ⊆ the token's scope.

Stripe Connect mapping
One Connect account per location

Each Sales Channel stores its Stripe Connect account ID in metadata. The platform charges the customer; the platform fee stays in the platform account; the remainder transfers to the location's connected account. Vienna's transfers happen in EUR with no FX (both eurozone).

13 · Security & Reliability

Built To Last

The Cal.com closed-source story is the active reminder. Public open-source code + AI assistance lowers the bar for vulnerability discovery. We design accordingly.

Secrets management
No keys in code · Doppler or 1Password Secrets Automation

Stripe live keys, Bókun API tokens, DB passwords — none of these touch a repository. Production injects them at runtime via the platform's secret store. Local development uses a separate set of test/dev keys.

Authentication
Customers: passwordless email + magic link · Staff: JWT

Customers don't get passwords — magic-link only. Reduces credential stuffing surface to zero. Staff use JWT with 8-hour expiry plus refresh-token rotation. MFA enforced on all staff with channel-scope greater than their own location.

Rate limiting
Per-IP and per-account · Redis-backed

Availability endpoint: 60 requests/minute/IP. Booking creation: 5 attempts/minute/account. Voucher validation: 10 attempts/minute/IP (prevents code-guessing). Webhook endpoints: signature-verified, no rate limit but per-source.

Input validation
Zod schemas at every public boundary

Every API route validates its body against a Zod schema before any business logic runs. Internal calls between modules use typed interfaces (TypeScript). Webhooks validate payload structure even after signature verification.

Audit log
Every state change with who/when/what

A separate audit_log table captures: actor (user or system), action, resource, before/after diff, timestamp. Inserts append-only — no updates, no deletes. Retained 7 years for accounting compliance.

Disaster recovery
Backups + drills · Monthly restore test

Nightly Postgres dumps to R2. R2 has its own redundancy. We run a monthly restore drill — spin up a fresh DB from yesterday's backup and verify a known booking exists. Once a quarter, full DR drill — bring up the entire stack from cold in a separate region.

16 · Confidence vs Headaches

What We Know,
What Could Bite

Honest engineering self-assessment. Three buckets — high confidence (we know how to do this well), medium (knowable but needs care), and concerns (real headache potential if rushed).

High Confidence
We Know How to Do This Well

Solved patterns, well-documented, large community knowledge. Build with normal care.

  • Medusa module + workflow setup — patterns are well-documented
  • Next.js storefront + admin extensions — standard React
  • Stripe integration — best documentation in the industry
  • Sentry + monitoring — 30-minute setup, just do it
  • Documenso + Twenty API integration — REST, straightforward
  • R2 storage + signed URLs — S3-compatible, well-trodden
  • BullMQ job scheduling — mature, reliable
  • Customer notifications (Novu) — adapter is small
  • Audit logging — append-only table, simple discipline
Medium Confidence
Doable With Real Care

Solvable, but the cost of being sloppy is high. Allocate buffer.

  • Bókun API integration — docs variable; needs defensive client
  • Stripe Connect with separate charges + transfers — easy to get wrong day one; expensive to refactor
  • Timezone + DST handling for availability — Cal.diy reference helps
  • Multi-tenant scoping — requires explicit tests, can be subtle
  • Voucher partial redemptions (JSMD rules) — needs JSMD docs + clear business rules
  • DATEV export format — well-defined but accountant-specific account mappings
  • Recurring slot logic + exceptions — booked patterns + holidays + weather closures interact
  • OTA receivables tracking — needs careful state modelling
Real Concerns
Could Bite Hard

Has caused outages and rewrites in other projects. Get these right or they will hurt.

  • Race conditions on the last slot — needs all three defences + load test, no shortcuts
  • Webhook reliability (Bókun, Stripe, Documenso) — they can be dropped, retried, duplicated; idempotency everywhere
  • Schema migrations on a live system — every migration tested in staging with prod-size data first
  • AGPL boundary discipline (Documenso, Twenty) — one PR that imports their source instead of calling the API = legal exposure
  • OTA payment reconciliation — when does the money arrive? from where? in what currency? matched to which booking?
  • Refund logic for OTA bookings — we don't refund — they do — but our system must reflect both states
  • Self-hosted Novu + Documenso operational load — backups, upgrades, monitoring of these too
  • Stripe dispute defense — assembling evidence quickly when a customer charges back
  • The first DATEV export reviewed by the accountant — almost certainly needs adjustments; build the iteration loop into the timeline
The Single Biggest Risk
Going Live Without Load-Testing the Booking Race Condition

Most other risks have soft consequences — a bad DATEV export gets resubmitted; a Novu downtime delays a notification by an hour. The booking race condition is the only one where the failure mode is visible to a real paying customer as a broken transaction, and that's the one that has to be bulletproof before any external traffic.
